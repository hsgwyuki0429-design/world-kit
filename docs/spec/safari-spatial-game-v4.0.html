Safari Spatial Game Prototype

Version 4.0 — AI実装統合・実機検証・Spatial Game技術仕様書

Target: iPhone Safari / iOS 26+ / HTTPS / 実機
Primary Goal: Safariで実際に取得できるデータだけから現実空間を観測・追跡し、ゲームが利用できる空間情報を取得する。
Game Goal: 現実の床・壁・家具などの形状や位置をゲーム空間として利用し、その場にゴール・障害物・ボールゲームを自動生成する。

本書は企画書ではなく、AIコーディングエージェントが直接実装に使用する統合技術仕様書である。

AIは、本書を「参考アイデア」として扱ってはならない。

本書に記載された以下を実装上の強制仕様とする。

● 禁止

AIがより簡単な実装を思いついた場合でも、それによってReal Data性、Correctness、Robustness、Reproducibility、Data Integrityが低下する場合は採用してはならない。

1. Version 4.0で追加された最重要思想

Version 4.0では、Version 3.0までの「本物のデータだけを使う」という思想を維持したまま、Spatial Worldを最終成果物ではなくゲーム体験を成立させるための内部基盤として扱う。

1.1 成功とはUI完成ではない

以下だけでは完成と認めない。

● Cameraが映る

● Feature Pointが表示される

● Tracking GOODと表示される

● 3D点が表示される

● Planeが表示される

● Coverageが増える

● Ballが飛ぶ

これらは内部データが正しい場合にのみ意味を持つ。

1.2 Single Source of Truth

ゲームに利用するSpatial情報の唯一の正規データ源はSpatialWorldとする。

以下が独自の空間データを保持してはならない。

● GameEngine

● CollisionSystem

● Renderer

● Debug UI

● UI state

● temporary visual mock

Game、Stage Generator、Collision、Renderer、DebugはSpatialWorldを参照し、独自の現実空間データを勝手に生成・保持しない。

1.3 Observable State

内部状態は可能な限り外部から検証可能にする。

最低限、以下を観測可能にする。

● Feature Count

● Tracked Count

● Match Count

● Inlier Count

● Inlier Ratio

● Reprojection Error

● Pose Confidence

● Keyframe Count

● Landmark Count

● Plane Count

● Coverage

● Tracking State

● Mapping State

● GPU/CPU Mode

● Frame Time

● Memory Pressure

1.4 Fail Closed

不確実な場合、AIは「成功」と判断してはならない。

例：

Depthを取得できない
→ DEPTH: UNAVAILABLE

Scaleが分からない
→ SCALE: UNKNOWN

Pose信頼度が低い
→ POSE: LOW CONFIDENCE

Plane確信度が低い
→ PLANE: UNKNOWN

Trackingに失敗
→ TRACKING: LOST

実データが存在しない
→ そのデータを生成しない。

14. Version 4.0 Final Vision

このアプリの最終目的は「現実空間をきれいな3Dモデルとして保存すること」ではない。現実空間をゲームが理解できる状態にし、その場そのものを遊び場へ変換することである。

ユーザーがスマートフォンを持って部屋を見回すと、床・壁・机・椅子・ソファなど、実際に観測できた空間情報をもとにゲームステージが構成される。

その上にゲーム用のリング、ターゲット、スタート地点などが配置され、ユーザーはボールを現実空間の形に沿って投げる。

最終体験

現実空間 → Camera → Tracking → Spatial Understanding → Spatial World → Game Stage Generation → Goal Placement → Ball Physics → Gameplay

「部屋をスキャンすること」自体は目的ではなく、「その部屋で遊べるゲームを生成すること」が目的である。

15. Core Product Definition

● Real Camera Data Only

● Real Tracking / Pose Data

● Observed Spatial Surfaces

● Spatial World as Single Source of Truth

● Procedurally generated game elements

● Physical ball interaction

● Real-space dependent collision

3Dモデルファイルの出力、汎用3Dアセットへの変換、完全な部屋の再現はPrototype v1の必須条件から外す。

16. Spatial World Policy

SpatialWorldは「現実空間の完全な3Dデータ」ではなく、「ゲームが必要とする観測済み空間情報の集合」と定義する。

最低限保持する情報

● Camera Pose History

● Tracked Landmarks

● Plane / Surface Candidates

● Surface Orientation

● Surface Confidence

● Approximate Spatial Relationships

● World Origin

● Tracking / Mapping Confidence

不要な情報を無理に生成しない。観測できない形状を推測して完全なGeometryとして扱わない。

17. Phase 5 — Geometric Verification

Phase 4までに取得したFeature Correspondenceを、RANSAC等で検証し、安定したPose推定に利用できる対応点だけを残す。

Pass

Outlierが十分除外され、Pose計算へ利用可能なInlierが安定して得られること。

18. Phase 6 — Relative Pose

Cameraの相対的な移動と回転を推定する。ゲーム空間の基準座標を保つために利用する。

Absolute scaleを保証できない場合はLOCAL UNITSとして扱い、無条件に1 unit = 1 meterと仮定しない。

19. Phase 7 — IMU Support / Fusion

Visual Poseを中心に、利用可能なMotion / Orientation情報を補助として利用する。

IMU単独で長時間の絶対位置を生成しない。

20. Phase 8 — Keyframe System

空間理解に有効な視点をKeyframeとして保持し、カメラ移動による観測情報を時系列で安定させる。

Keyframeはゲーム開始後も必要に応じて更新し、古い情報を盲目的に永久利用しない。

21. Phase 9 — Triangulation

十分な視差がある観測だけからSparse Spatial Informationを取得する。

低視差から無理に大量の3D点を生成しない。Sparse informationは空間理解と追跡を補助するために利用する。

22. Phase 10 — Landmark Map

観測されたLandmarkを時系列で管理し、Camera PoseとSpatial Worldの安定性を支える。

Landmark Map自体を最終的な3Dモデルとして扱わない。

23. Phase 11 — Surface Understanding

現実空間をゲームに利用するため、床・壁・水平面・その他の安定した表面候補を検出する。

優先順位

● Floor / Ground-like Surface

● Large Horizontal Surface

● Vertical Surface / Wall

● Obstacle-like Surface

● Unknown Surface

単一Frameだけで家具の種類を断定しない。ゲームに必要な「当たり面」「支え面」「遮蔽面」が得られることを優先する。

24. Spatial Object Classification

ゲーム生成に必要な範囲で、Spatial Objectを「意味のあるゲーム用カテゴリ」に分類する。

● GROUND

● WALL

● PLATFORM

● OBSTACLE SURFACE

● UNKNOWN

「机」「椅子」「ソファ」などの物体名認識は必須条件ではない。まず、実際にゲームで利用できる表面の位置・向き・大きさ・信頼度を取得する。

25. Spatial World Runtime State

SpatialWorldは常時更新され、ゲームはその最新の信頼できる状態を参照する。

● World Origin

● Camera Pose

● Surface List

● Landmark Quality

● Tracking State

● Mapping State

● Confidence

● Last Updated Timestamp

低Confidenceの情報は、ゲーム生成やCollisionで重要度を下げるか使用禁止にする。

26. Game World Abstraction

SpatialWorldからゲームが利用する抽象化レイヤーを生成する。これは3Dモデル変換ではなく、「ゲームに必要な地形情報の解釈」である。

例：床候補 → ボールが転がる面、垂直面 → 反射・停止可能な面、高さのある水平面 → ボールが乗る/落ちる可能性のある面。

27. Game Stage Generator

実際に観測されたSpatial Worldを入力として、プレイ可能なステージを自動生成する。

生成要素

● Start Point

● Target Ring / Goal

● Optional Checkpoint

● Optional Boundary

● Optional Visual Guidance

固定された部屋形状に合わせてステージを作らず、その場で得られた空間情報から生成する。

28. Goal Ring Generation

ゲームの代表的なゴールとしてリングを生成する。リング位置は「適当に空中に置く」のではなく、Spatial Worldの形状とCamera / Playerの位置関係から決定する。

Placement Constraints

● 十分なConfidenceのある空間内に置く

● 現実物体内部へ埋め込まない

● 到達可能性を考慮する

● 画面から視認可能な位置を優先する

● ユーザーが狙いを作れる距離・高さに調整する

29. Goal Difficulty

環境の違いによって難易度を自動調整する。

● EASY: 床上・近距離・障害物少

● NORMAL: 障害物回避や角度調整が必要

● HARD: バウンド・狭い隙間・高低差を利用

● EXPERT: 複数の現実物体を利用した複雑な経路

難易度はランダム値だけでは決めず、観測されたSpatial Worldの条件から算出する。

30. Start Point Generation

ボールを放つ開始地点を、ユーザーが安全かつ操作しやすい場所に生成する。

● User reachable area

● Clear line of sight to target

● Sufficient free space

● Stable ground or virtual spawn plane

31. Ball Interaction Model

プレイヤーは画面操作によってボールの投射方向と強さを決定する。

基本操作

● Aim Direction

● Charge / Power

● Release

● Optional Spin / Curve in later version

ボールの物理挙動はSpatial World由来のCollision Surfaceを参照する。見えない固定壁をゲーム都合で設置してはいけない。

32. Ball Physics

ボールには重力、速度、反発、摩擦、Collisionを適用する。

● Position

● Velocity

● Acceleration / Gravity

● Radius

● Mass

● Restitution

● Friction

現実空間のScaleが未知の場合、ゲーム内のLOCAL UNITSとボールサイズを一貫させ、無根拠な実寸換算をしない。

33. Collision Policy

Collisionの唯一の空間情報源はSpatialWorldから生成された実測ベースのSurface情報とする。

● No Fixed Invisible Wall

● No Fake Floor

● No Random Collision Surface

● Collision Surface Confidence Required

● Collision Provenance Logged

ゲームプレイを成立させるために必要な仮想オブジェクトは生成してよい。ただし、それが「現実空間のCollision」と偽装されてはならない。

34. Goal Collision / Success

ボールがリング内部のGoal Volumeを通過した場合にSuccessとする。

● Ball enters target volume

● Velocity / direction constraints if stage requires

● Target remains spatially stable

● Success state is observable and logged

35. Procedural Stage Validation

自動生成されたステージが「遊べる」と判断できるか検証する。

● Start and Goal are inside known space

● Goal is not embedded in obstacles

● Target is visible or reasonably discoverable

● At least one plausible ball trajectory exists

● Collision geometry is stable

完全な数学的解の保証をPrototype v1の必須条件にはしないが、明らかに到達不能なゴールはRejectする。

36. Stage Regeneration

Tracking / Mappingにより空間認識が大きく更新された場合、ゲームステージを更新できる。

● Confidence improved → refine stage

● Spatial contradiction → invalidate affected object

● Goal becomes blocked → regenerate goal

● Tracking lost → freeze gameplay or request rescan

37. Game State Machine

ゲーム状態を明確に分離する。

● SCAN

● SPATIALIZING

● STAGE_GENERATING

● READY

● AIMING

● THROWING

● SUCCESS

● RETRY

● PAUSED

● TRACKING_LOST

状態とUI表示は必ず一致する。

38. UI / AR Presentation

カメラ映像を中心とし、その上にゲーム要素を重ねる。

● Target Ring

● Start Indicator

● Aim Guide

● Power Indicator

● Ball

● Success Feedback

● Tracking Warning

現実の家具そのものを完全に3D再現して表示する必要はない。ゲームに必要なリング・ガイド・ボール等を明確に表示する。

39. SCAN Screen

ユーザーが部屋をゆっくり見回す画面。

表示例：TRACKING GOOD / SURFACES 12 / CONFIDENCE 0.84 / READY AREA 4

すべて実測値。

40. GAME Screen

● Camera View

● Target Ring

● Ball

● Retry

● Tracking State

41. No 3D Export Requirement

Prototype v1では、OBJ / GLB / USDZ等の汎用3Dデータとしての書き出しを要求しない。

保存対象はゲーム再開に必要なSpatialWorldとGame Stateに限定する。

42. Save / Resume

必要に応じてSpatialWorld、Stage Seed、Goal、Game Stateを保存できる。

● SpatialWorld runtime state

● Stage generation parameters

● Goal pose

● Game progress

● Confidence / provenance

43. Performance Architecture

Spatial trackingとゲーム描画・物理を同時に実行しても、iPhoneで継続利用できる性能を目標とする。

● Heavy vision processing off UI Thread

● Adaptive tracking rate

● Lightweight collision representation

● Particle / effect limits

● Memory pressure monitoring

44. Fail Closed

空間情報の信頼性が不足した場合は、ゲームを都合よく成立させるのではなく状態を下げる。

● TRACKING LOST → pause or rescan

● SURFACE UNKNOWN → do not use for collision

● GOAL INVALID → regenerate

● POSE LOW CONFIDENCE → do not commit new stage state

45. Absolute Prohibitions

● Fake ARKit / RoomPlan data

● Fake Depth / LiDAR

● Fixed Floor / Fixed Wall as reality collision

● Fake Coverage

● Fake Confidence

● Invisible fixed collision

● Goal placed using nonexistent geometry

● Game success based on data unrelated to observed space

46. Development Architecture

CaptureManager → TrackingEngine → Spatial Understanding → SpatialWorld → StageGenerator → GameWorld → BallPhysics / Collision → Renderer / UI

GameWorldはSpatialWorldを入力とし、現実空間の代わりになる独自Geometryを勝手に生成しない。

58. 最終的な成功の定義

ユーザーがスマートフォンを持って自分の部屋を見回す。すると、その部屋の床・壁・家具など、実際に観測された空間の特徴を利用して、その場専用のゲームステージが生成される。

ユーザーは現実の空間を見ながらボールを投げ、現実空間に合わせて生成されたリングを狙う。ボールの挙動とCollisionは実際に観測された空間情報に依存する。

これがVersion 4.0の最終成功条件である。

60. Final Declaration

このプロジェクトは、現実空間を観測・追跡し、その空間情報を使ってゲームを生成するSpatial Gameである。

現実の部屋ごとに異なる地形が生まれ、その地形に合わせてリングやゴールが配置され、プレイヤーはボールを投げて攻略する。

3Dデータの完全な再構成は目的ではない。現実空間そのものを、遊べるゲームステージとして利用することが目的である。
